# 벤 답변 전달력 분석(1단계) — 설계 (spec, 백엔드)

- 생성일시: 2026-10-16
- 수정일시: 2026-10-16
- 이슈: #91 (1단계만. 2단계 "목소리 자신감"은 별도 설계)

## 0. 배경 · 위치

벤(프리미엄 면접관) 리포트는 답변 **내용**만 평가한다. 녹음은 저장·재생만 되고 분석에 쓰이지 않는다.
1단계는 답변의 **전달력**(말 속도, 쉼, 첫마디까지 걸린 시간, 군말 경향)을 리포트에 넣는다.

측정은 **브라우저**가 한다(프론트 담당 — 이슈로 요청). 브라우저는 답변마다 이미 잘라 둔 벤 녹음을 Web Audio로 분석해 **숫자만** 만들고, 리포트 요청에 실어 보낸다. 소리는 서버·Claude로 가지 않는다.
이 spec은 **백엔드 몫**만 정한다: 측정값을 받는 계약, 규칙 판정, 벤 리포트 프롬프트, 보관함 저장.

## 1. 목표 · 비목표

### 목표
- 리포트 요청이 답변별 측정값(`delivery`)을 선택으로 받는다.
- 서버가 측정값을 **정해진 기준표로 판정**한다(모델이 숫자를 해석하지 않게).
- 측정값이 있으면 벤이 리포트 문항마다 `delivery`(전달력 피드백 한두 문장)를 더 쓴다.
- 측정값이 없으면 요청·프롬프트·리포트가 지금과 **바이트 단위로 같다**.
- 보관함에 저장하는 리포트 문항이 `delivery`를 잃지 않는다.

### 비목표
- 브라우저 측정 구현, 리포트 화면 표시(프론트 — 이슈 #91 후속 프론트 이슈)
- 로컬 면접관(데이빗·쥴리·올리비아) 리포트 — 벤 전용
- 목소리 자신감(음높이·떨림·크기 안정성) — 2단계
- 측정값을 서버에 따로 저장 — 결과는 리포트 원문 안에만 남는다

## 2. 데이터 · 계약

`/api` 계약 변경 **있음 — 전부 additive**. `docs/API.md` 먼저 갱신, 백엔드 배포 후 프론트(lockstep).

### 2.1 `POST /api/premium/interviews/{id}/report` — 선택 본문

지금은 본문 없는 요청이다. 선택 본문을 받는다(없거나 `{}`이면 지금과 같음).

```jsonc
{ "delivery": [
  { "answer": 1,             // 몇 번째 사용자 답변인지(1부터, 면접 대화의 답변 순서)
    "speechSec": 42.5,       // 실제로 말한 시간(초, 쉼 제외)
    "syllables": 210,        // 받아쓴 텍스트의 음절(한글 글자) 수
    "longPauses": 3,         // 2초 이상 쉼 횟수
    "longestPauseSec": 4.1,  // 가장 긴 쉼(초)
    "firstWordSec": 2.8,     // 질문이 끝난 뒤 첫마디까지(초)
    "fillerLevel": "high" }  // "low" | "normal" | "high" | null(측정 불가)
] }
```

- 검증(위반 시 `422 {"error":"invalid","field":"delivery"}`, Claude를 부르지 않음):
  - 항목 수 0~8, `answer`는 1 이상이고 서로 달라야 하며 이 면접의 실제 답변 수 이하
  - `speechSec` 0~600, `syllables` 0~5,000(정수), `longPauses` 0~200(정수), `longestPauseSec` 0~600, `firstWordSec` 0~600
  - `fillerLevel`은 위 셋 또는 `null`
- 타이핑으로 답한 답변, 측정이 불가능한 답변은 프론트가 **빼고** 보낸다(서버는 없는 답변을 "측정 없음"으로 본다).
- 이미 만든 리포트를 다시 요청하면(`done`) 지금처럼 보관한 원문을 그대로 다시 보내고 본문은 무시한다.
- 응답 SSE 형태는 그대로. 리포트 원문 JSON 문항에 선택 칸 `delivery`(문자열)가 붙을 수 있다(2.3).

### 2.2 판정 기준(서버 규칙, `app/llm/delivery.py`)

답변별:

| 항목 | 계산 | 판정 |
|---|---|---|
| 말 속도 | 분당 음절 = `syllables ÷ speechSec × 60` | 250 미만 "느림", 250~330 "보통", 330 초과 "빠름" |
| 긴 쉼 | 말한 1분당 횟수 = `longPauses ÷ max(speechSec/60, 0.5)` | 1 이하 "적음", 2 이하 "보통", 2 초과 "잦음" |
| 첫마디까지 | `firstWordSec` | 3초 이하 "보통", 3초 초과 "망설임 긺" |
| 군말 | `fillerLevel` 그대로 | "적음"/"보통"/"잦은 경향"(단정하지 않음), `null`이면 언급 안 함 |

- `speechSec`가 5초 미만인 답변은 "측정 부족"으로 판정을 생략한다.
- **개인 기준 비교:** 1번 답변(자기소개)이 측정됐으면 그것을 기준으로, 다른 답변의 분당 음절·긴 쉼 비율이 기준의 1.5배 이상 또는 0.67배 이하이면 "기준 대비 ○배"를 덧붙인다.
- 기준값은 모듈 상수로 두고 테스트로 고정한다.

### 2.3 벤 리포트 프롬프트(`app/llm/prompts.py`, 계층 규율 경로)

측정값이 **있을 때만** 리포트 지시문 뒤에 벤 전용 문단을 붙인다(없으면 지금과 같으므로 프론트와의 동기화 테스트 `test_prompt_parity.py`에 영향 없음).

문단 내용(요지 — 문구는 구현 때 확정):
- `[답변별 전달력 측정]` 블록: 답변 번호마다 숫자와 판정 한 줄(예: `답변 3: 분당 352음절(빠름), 2초 이상 쉼 4회·말한 1분당 3.1회(잦음), 첫마디까지 4.2초(망설임 긺), 군말 잦은 경향, 기준 대비 쉼 2.1배`)
- 지시: "각 문항 객체에 `delivery` 칸을 더해, 그 문항에 속한 답변(꼬리질문 답 포함)의 전달력을 한두 문장으로 쓴다. 판정과 숫자를 근거로 들고, 고칠 방법을 하나 제시한다. 군말은 '경향'으로만 말한다. 측정이 없는 답변만으로 된 문항에는 `delivery`를 쓰지 않는다."
- 측정 블록은 지원자 자료가 아니라 서버가 만든 숫자이므로 별도 안내 없이 넣되, 숫자·판정 문자열만 들어간다(사용자 텍스트 없음).

출력 형태: 문항 `{question, answerSummary, feedback, delivery?}`. 지금 프론트 파서(`frontend/src/utils/reportParser.ts`)는 필수 세 칸만 검사하고 나머지를 보존하므로 백엔드를 먼저 배포해도 깨지지 않는다.

### 2.4 보관함 저장

`app/schemas.py`의 보관함 `ReportItem`에 선택 칸 `delivery: str | None`(최대 2,000자)을 추가한다. 지금은 모르는 칸이 버려져서, 프론트가 보관할 때 `delivery`가 사라진다. 응답에도 있으면 그대로 돌려준다(additive).

## 3. 접근 제어 / 제약

- **개인정보:** 서버·Claude로 가는 건 숫자와 판정 문자열뿐이다. 소리·받아쓴 텍스트를 추가로 보내지 않는다(대화 본문은 원래 벤에게 간다). 측정값을 로그에 남기지 않는다.
- **비용:** 측정 블록은 답변당 한 줄(수십 토큰)이라 리포트 1회 비용 변화는 미미하다. 출력은 문항당 한두 문장이 늘어난다.
- **남용:** 기존 요청 제한(분당 6회)·시도 상한 그대로. 검증 실패는 시도를 세지 않는다(Claude 호출 전 422).

## 5. 영역별 영향

- backend: 2.1~2.4, `docs/API.md`.
- frontend(@leemonta9482에게 이슈로 요청):
  1. 측정: 벤 답변 녹음(이미 답변마다 잘라 둠)을 Web Audio로 디코드 → 말 구간 판별(에너지 기준, 잡음이 문제면 Silero VAD) → `speechSec`·`longPauses`·`longestPauseSec`, 질문 재생 종료~첫 말소리로 `firstWordSec`, 받아쓴 텍스트 한글 글자 수로 `syllables`, 길게 끄는 같은 높이 모음 구간으로 `fillerLevel`(정확도 중간 → 경향만)
  2. 리포트 요청에 `delivery` 실어 보내기(타이핑 답변·측정 불가는 제외)
  3. 리포트·보관함 화면에 측정값과 `delivery` 표시 — **표시 방식은 아직 미정, 논의 후 결정**
  4. 출시 전 샘플 답변 10~20개로 사람 측정(또는 Praat)과 비교해 오차 확인
- deploy / finetune: 없음.

## 6. 무회귀 · 롤아웃

- 본문 없는 리포트 요청은 지금과 같다(테스트로 고정). 측정값이 없으면 리포트 지시문이 바이트 단위로 같다.
- 배포 순서: 백엔드 PR(계약·판정·프롬프트·보관함 칸·`docs/API.md`) → dev 머지 → demomo에서 curl로 측정값을 넣은 벤 리포트 1회 확인(`delivery` 칸 생성·JSON 파싱) → 프론트 이슈 진행.

## 8. 성공 기준

- 백엔드 테스트: 본문 없음/빈 `delivery` → 지금과 동일, 검증 실패 → 422·Claude 미호출·시도 미증가, 판정 경계값(250·330, 1·2회/분, 3초, 5초 미만 생략, 기준 대비 1.5배·0.67배), 측정 블록이 리포트 지시문 뒤에 붙음, `done` 재요청은 본문 무시, 보관함이 `delivery`를 보존.
- demomo: 벤 면접 1회 후 측정값을 넣은 리포트 요청 → 문항에 `delivery` 생성, 숫자 근거 포함, JSON 파싱 정상.
